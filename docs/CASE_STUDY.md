# Stillroom — portfolio case-study draft

Stillroom explores a focused question: how can a personal file library feel calm while keeping sharing explicit? Inspired by a cloud-storage tutorial, the implementation gives the concept a monochrome editorial interface with pastel color blocks adapted from the supplied design specification, and a small set of file actions.

The application uses Next.js, TypeScript and Appwrite. The browser interacts with same-origin server routes; server-side session checks determine ownership and recipient access before files are returned. Owners manage files and sharing, while recipients receive view/download access only. The design includes a verified-email gate, bounded uploads, safe previews and cursor-based browsing.

A central engineering challenge is that object storage and database writes cannot be committed as one transaction. Stillroom records pending uploads and unfinished deletions so failures remain visible and recoverable. Database transactions update ready-file totals alongside metadata state changes. This avoids loading the entire library for the dashboard and avoids claiming success when a storage operation is uncertain.

Local tests exercise validation and partial failures through a simulated provider boundary. Separate live checks against the authorized Free NYC Appwrite project passed file lifecycle, original-byte download integrity, owner/recipient isolation, revocation, transactional totals, direct SDK permission denials and two-page owned/shared queries. Seeded real-provider checks cover pending protection, cleanup recovery and rate-limit exhaustion. The authenticated interface passed desktop and mobile browser checks. Disposable accounts were administratively verified, so those tests do not establish verification-email delivery. No reliability, performance, usage or business metrics are claimed.

A subsequent update adds verified invitation binding, active-member checks, server-only metadata, reversible suspension tooling and restricted logging. Its Cloud migration and bounded live protocol passed, including restoration, rejection of old sessions, preserved-file hashes and direct provider denials. Both temporary operator keys were revoked and the disposable accounts left disabled. Local/mock tests and actual local logging checks remain separate from that live evidence; external logging and direct-registration abuse remain unresolved. See the beta-readiness checklist for the remaining operating-policy and release gates.

A later bounded live account-exit protocol verified removal of a designated disposable owner's active resources, sharing-reference cleanup, session rejection and preservation of the control account/file and pre-existing resources. This establishes logical application/provider deletion within that protocol, not erasure of backups, infrastructure logs or recipients' downloads. Prospective terms controls are locally implemented but remain disabled with a null publication manifest.

The operator chose a local portfolio demonstration rather than funding a hosted beta. The application has not been deployed. Remaining hosted-release checks include resource-abuse containment, host/private-record backup recovery, operational notices and real outages, concurrency stress, all supported media and maximum-size paths, and provider processing thresholds. Source publication is distinct from those operating commitments. This draft does not assert personal motivations, individual ownership of a team effort, or user impact that has not been supplied.

The final portfolio review used a finite checklist rather than extending beta operations. It corrected upload labeling and form-control border contrast, exercised actual components with simulated file actions, and inspected unconfigured production routes without original private records. Automated accessibility checks and rendered screenshots supplement keyboard/role assertions; they are not screen-reader certification.

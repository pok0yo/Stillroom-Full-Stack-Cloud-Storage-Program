## Actual lifecycle and policy gaps

1. Upload creates a private pending metadata row, writes storage, then transactionally marks ready and updates totals. Uncertain failures preserve a journal. Pending uploads require operator recovery after draining upload workers; no automatic expiration job. See SETUP.md.
2. Owner Delete marks deleting, empties recipients, adjusts ready-file totals, deletes stored bytes, then metadata. Failure leaves retryable state; successful API return is not proof of physical media/backup erasure. There is no user trash/restore feature. Recipient-held copies remain.
3. Suspension marks membership suspended, disables provider account when operator scope permits, revokes sessions and removes that account's recipient access. It preserves owned files, totals, account and binding. Other active recipients of the suspended owner's files are not automatically stripped by this procedure. This describes suspension only; the separately tested account-exit procedure restricts all owned files before removal.
4. Authenticated operator-mediated active-resource exit passed live testing, including recipient revocation, preservation of other owners’ files, stale-plan rejection and hold/retry. It is not fully self-service or erasure of every residual record/provider copy. No automatic inactivity cleanup, shutdown-notice mechanism, complete account-data export or retention scheduler exists. The current UI supports individual-file downloads.

It describes seven-day database recovery/retention, with some databases backed up every four hours. This does **not** establish erasure of Storage objects, authentication data or every copy seven days after a user deletes a file, nor a restore entitlement on Free.
